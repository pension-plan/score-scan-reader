Spike: pretrained ML OMR models in the browser

Date: 2026-11-08. Scope: can a pretrained, permissively licensed optical-music-recognition model run client-side (onnxruntime-web, self-hosted wasm, artifact CSP, files of 15 MB or less, 64 MB in total) and help with the two hard requirements: scanned closed-score SATB with voice separation, and lyrics? Everything here was measured on this machine (Linux aarch64, 192 cores) unless a number is quoted from a model card. Code, data and raw logs are in spike/ml/, and every table can be regenerated (see "Reproduce").

Recommendation (TL;DR)

  1. Use the copista-2m symbol detector (KobiMusic, Apache-2.0 weights and code, https://huggingface.co/kobimusic/copista-2m, HF sha c37d89e1e52edc95c1a73bda0aea5f2f71a9c763). I exported it to ONNX as two graphs and stored the weights as int8 (int8w): 1.77 MB + 0.29 MB = 2.06 MB (spike/ml/assets/). The page-level JS pipeline is spike/ml/src/copista_core.mjs: plain array code with no dependencies, and it runs unchanged in node and in the browser.
    • On the 36 test scans (3 pieces × 200/300 dpi × 6 degradations), run through onnxruntime-web wasm: notehead P 1.000 / R 0.991 / F1 0.996, staff-position accuracy 1.000 on everything except a harsh photocopy (0.65), stem direction 0.984, and voice-slot accuracy 0.991 on the closed-score SATB. The model itself says "voice 1 (stem up) / voice 2 (stem down)" for every notehead, which gives S/A and T/B part separation almost for free.
    • Speed, one wasm thread (the realistic artifact case, since there is no cross-origin isolation): ≈4.2–5.1 s per A4 page in headless Chromium, end to end (resample, dense CNN ≈4.0–4.7 s, verifier ≈0.1 s, decode).
    • Quantization costs nothing. fp32, fp16-weight and int8-weight variants give identical scores. Do not use ORT dynamic int8 (int8d): it is 2× faster in native ORT but 3× slower in wasm (12.2 s vs 4.1 s).
  2. Runtime: onnxruntime-web 1.30.0 (MIT). Load ort.wasm.bundle.min.mjs from jsdelivr or cdnjs with a dynamic import() inside a blob: module worker, and set ort.env.wasm.wasmPaths = { wasm: <absolute URL of self-hosted ort-wasm-simd-threaded.wasm> } (14,239,897 bytes, which fits under 15 MB). This passes an artifact-like strict CSP (no 'self' in script-src). Fallback: onnxruntime-web 1.18.0 UMD (ort.wasm.min.js via <script src> or importScripts in a blob worker, wasmPaths = 'assets/', self-host ort-wasm-simd.wasm, 10.6 MB). It is about 10–20 % slower but uses the simplest loading path. Things that fail under that CSP (measured): every ORT ≥ 1.19 UMD build, and an ESM bundle given a string wasmPaths. Both try to import() ort-wasm-simd-threaded.mjs from the same origin. A static import … from <CDN> inside a blob module worker also fails.
  3. Do not use homr (AGPL-3.0; at least 75 MB of weights even after quantization; minutes per page in wasm; no voice separation, since closed score comes out as chords: voice accuracy 0.46). Do not use oemer (MIT but 109 MB fp32, which needs splitting; about 33 min/page of wasm compute; measure-pitch F1 0.20–0.44 on our scans; breaks with OpenCV 5). Do not use a YOLO/DeepScoresV2 detector: none with a permissive licence exists. The Ultralytics-trained ones carry AGPL-3.0, others have no licence, and DeepScoresV2 itself is CC BY 4.0. satb-line-omr (MIT, 6.4 MB, built for the browser) is excellent on clean open-score prints (100 % pitch), but by design it reads one voice per staff (closed score: 17 % notes), and its staff finder found 0 staves on every rotated/scanned/photocopied page. At most it is an optional extra.
  4. What ML does not give us:
    • Lyrics. copista has no text classes. Lyrics still need the Tesseract path; the detector's notehead and system boxes give the text bands.
    • Rhythm and measure assembly into MusicXML. This must be written in JS from the detections (noteheads with duration class, dots, voice_slot, stem_dir and staff_position; plus barlines, measure boxes, clefs, key/meter signatures, rests, beams, ties/slurs). An alternative is to port copisteria's Apache-2.0 reader (about 4,000 lines of Python plus a 2.03 M-param evidence transformer). On these hymn scans the detector's raw readings are already more accurate (F1 0.996) than copisteria's full reader output (measure-pitch F1 0.93 with the 2m detector), so a simple JS assembler is the right first step.
  5. Pitch from geometry, not only from the model. On broken-staff photocopies, copista's staff_position drops to 0.65 (2m) / 0.87 (28m), while notehead detection stays at F1 0.996. Compute pitch from the notehead's y relative to our own staff-line fit, and use the model's staff_position only as a cross-check.
  6. Optional "accurate" mode: copista-28m (Apache-2.0). Its int8 weights are 26.8 MB, so they must be split into two external-data files (13.7 + 13.0 MB; this loads in ort-web). It costs ≈47–60 s/page in wasm, and on our scans it only helps on the photocopy (staff-position 0.87 vs 0.65). Not worth shipping by default.

Budget for the recommended path: wasm 14.2 MB + models 2.1 MB + classes JSON 5 KB. That leaves about 47 MB of the 64 MB for Tesseract core, traineddata, pdf.js and the sample.

Test material (spike/ml/scans/)

  • Generator: spike/ml/src/make_scans.py, with pieces defined in src/pieces.py. All music is public domain.
    • melody_lyrics: Amazing Grace (NEW BRITAIN, text Newton 1779). G major, 3/4 with pickup, 2 verses, 4 melismas with extenders.
    • satb_closed: Old Hundredth (Genevan 1551) in a 4-part setting written for the spike. Closed score: S+A on the treble staff (\voiceOne/\voiceTwo), T+B on the bass staff, 2 verses between the staves. 128 notes, 12 bars.
    • satb_open: the same setting on 4 staves.
  • Pipeline:
    1. LilyPond 2.24 → PDF (A4, one page).
    2. pdftoppm -r 200|300 -gray.
    3. Six variants per page: clean; rot (1.3°); noiseblur (σ 1.1 px at 300 dpi + noise σ 14); jpeg (q30); scan (−0.8° plus a shift, uneven lighting, blur, noise, JPEG q55); photocopy (0.5°, blur + noise σ 25, hard threshold, speckle, median: broken and thickened lines).
    • Result: 36 images.
  • Ground truth:
    • scans/gt/<piece>.musicxml: MusicXML 4.0 partwise, one <part> per voice, lyrics with syllabic and extend.
    • scans/gt/<piece>.json: note lists.
    • scans/<image>.boxes.json: one box per notehead, labelled with voice and note index. LilyPond point-and-click link annotations in the PDF (\pointAndClickTypes #'note-event) are mapped through the textedit line:col back to the generated source, then pushed through the same affine transform as the degradation. 288/288 noteheads mapped, checked visually.
  • One real scan: scans/real/be_thou_1919.jpg, from Wikimedia Commons (public domain). Church Hymnal with Accompanying Tunes (1919), "Slane" in closed-score SATB, with show-through from the reverse page. No ground truth; used for a qualitative check only.

Accuracy

End-to-end, using each project's own Python pipeline (upper bound for what a port could do)

Metrics:

  • Measure-pitch F1: per-measure multiset of MIDI pitches, ignoring part and voice.
  • +duration F1: the same, with (pitch, duration) pairs.
  • Voice-assignment accuracy: predicted (part, staff, voice) streams are assigned one-to-one to the ground-truth voices (S/A/T/B or the melody), scoring LCS matches of (pitch, duration). A stream that holds chords can serve only one voice, so an unseparated closed score scores about 0.5.

The scorer is spike/ml/src/eval_xml.py. The ground-truth file scores 1.000 on every metric.

Detector-level: copista through the browser-portable pipeline (src/copista_core.mjs)

Predicted note_* boxes are matched one-to-one to ground-truth noteheads (centre within 0.6 notehead widths). Attribute accuracies are computed on matched notes:

  • staff position: half-spaces from the middle line, against ground-truth pitch and clef.
  • stem: closed score only, whole notes excluded.
  • voice slot: closed score only; S/T should be 1, A/B should be 2.

Scorer: src/eval_notes.py and src/score_dets.py. "web" means onnxruntime-web 1.30.0 wasm (run in node; Chromium gives identical detections, see below). "torch" means the authors' PyTorch detector inside copisteria. CPU ms is process CPU time per page, which is robust to the machine being shared (load average was often above 1000).

Staff-position accuracy is 1.000 on clean, rot, noise+blur, JPEG and scan for every 2m and 28m variant. On the photocopy it drops to 0.63–0.66 (2m) and 0.83–0.88 (28m). Detection itself stays at F1 0.995–0.997 there, which is why pitch should come from staff-line geometry.

Notes:

  • My ONNX export plus JS decode reproduces the PyTorch reference (identical P/R/F1, staff-position 0.943 vs 0.944).
  • The JS box-filter resample is used instead of PIL Lanczos and makes no measurable difference.
  • Where the remaining voice-slot errors (0.9 %) come from:
    • Stemless whole notes in the bass voice (two per page), where the model guesses voice 1. The assembler should resolve these from vertical order and rhythm: the lower whole note on a two-voice staff is voice 2.
    • One tight S/A second, read as stem_dir=both.
    • In addition, 1–3 noteheads per page are missed, each one note of a two-note chord on a stem.

Size and quantization (src/quantize.py)

Four variants were built for every model:

  • fp16w: initializers stored as fp16 with a Cast to fp32; compute stays fp32.
  • int8w: per-output-channel symmetric int8 initializers plus DequantizeLinear; compute stays fp32.
  • fp16: full fp16 graph via onnxconverter-common 1.16 with keep_io_types.
  • int8d: onnxruntime.quantization.quantize_dynamic, QInt8, per-channel.

Findings:

  • Weight-only storage (fp16w/int8w) is the right tool for wasm. It gives a ¼ size download at fp32 speed with no accuracy loss (copista: identical scores).
  • ORT dynamic int8 is 2× faster in native ORT but 2.5–3× slower in wasm: copista2m 12.2 s vs 4.1 s, 28m 133 s vs 47 s, oemer-seg 14.8 s vs 5.9 s, homr segnet 2.2 s vs 0.75 s.
  • Full fp16 graphs are slower or broken on CPU/wasm.
  • When opset-9 tf2onnx models (oemer) get weight-only transforms, they must first be upgraded with onnx.version_converter to opset 13; Slice changed from attributes to inputs.

Weights variants, multi-threading and external data on the working paths (strict CSP):

  • Detections in Chromium are identical to node (124 note boxes on this page for every variant).
  • Warm page times (1.30.0 ESM and 1.18.0 UMD): fp32 / fp16w / int8w are all 4.1–4.4 s; int8d is 11.6 s on 1.30.0.
  • int8d does not load at all on 1.18.0: "Could not find an implementation for ConvInteger(10)".
  • Always set ort.env.wasm.numThreads = 1. With numThreads=4, the 1.30.0 bundle fetches ort-wasm-simd-threaded.mjs from the CDN to start its thread workers, and connect-src blocks that ("no available backend"). This happened even with COOP/COEP headers sent; in this harness crossOriginIsolated stayed false, so the multi-thread upside was not measured. The artifact host cannot be assumed to send those headers anyway.
  • copista-28m int8w split into two external-data files loads via externalData: [{path, data: url}] and runs in ≈60 s.
  • Full numbers are in the matrix logs; see the appendix table generated by src/summarize.py (out/tables.md).

Loader that worked (ORT 1.30.0, strict CSP, off the main thread)

const BASE = new URL('.', location.href).href;            // blob: workers can't resolve relative URLs
const SRC = `
const ortP = import('https://cdn.jsdelivr.net/npm/onnxruntime-web@1.30.0/dist/ort.wasm.bundle.min.mjs');
self.onmessage = async ({ data }) => {
  const ort = await ortP;
  ort.env.wasm.numThreads = 1;
  ort.env.wasm.wasmPaths = { wasm: data.base + 'assets/ort-wasm-simd-threaded.wasm' };  // object form!
  const get = async (f) => new Uint8Array(await (await fetch(data.base + 'assets/' + f)).arrayBuffer());
  const dense = await ort.InferenceSession.create(await get('copista2m-dense.int8w.onnx'), { executionProviders: ['wasm'] });
  const rel   = await ort.InferenceSession.create(await get('copista2m-rel.int8w.onnx'),   { executionProviders: ['wasm'] });
  // ... copista_core.detect(ort, {dense, rel}, meta, data.gray) -> postMessage(dets)
};`;

How the detector maps onto the product requirements

  • Closed-score SATB → separate parts. For each staff, notes with voice_slot=1 (stems up) become S (treble) or T (bass), and voice_slot=2 become A or B. stem_dir=both on a shared head goes into both voices. A grand staff (brace, grpSym_brace) is not split. The bracket/brace class distinguishes choir staves from piano systems, which helps with the "do not split piano" rule.
  • Rhythm. Duration comes from the note class (note_whole … note_16th) plus the dots attribute, rests from the rest_* classes, and bar boundaries from barLine_* and measure boxes (one per staff per bar). Clefs, keySig_* and meterSig_N_D (82 meter classes) are all detected.
  • Pitch. Use our own staff-line fit with notehead y. Cross-check against staff_position and use it when the staff fit is unsure. Get the clef from the clef_* class.
  • Lyrics. Not covered. Run OCR on the band between the notehead boxes of adjacent staves, or below the system. Attach syllables by x to the voice that carries them: in a hymn the between-staves verses belong to S, and to A, T and B too when they are homorhythmic.

Caveats

  • Machine. The box was shared and heavily loaded (load average 500–1400 on 192 cores) while I measured. Wall times are noisy, which is why CPU ms is reported. Chromium numbers are single runs on aarch64.
  • Test data. The scans are synthetic, from LilyPond engraving, and the pieces are simple, homophonic hymn textures. copista was trained on varied engravings with scan effects, so the near-perfect detector numbers here are likely optimistic for 19th-century prints. The one real 1919 scan looked good, with a few misses, but it has no ground truth.
  • Python baselines. copisteria e2e numbers include its own Python reader. Our browser path would replace that with a JS assembler, so its accuracy is still to be built and measured.
  • Out of scope. Lyrics and OCR were not evaluated in this spike.
